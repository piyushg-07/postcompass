# Contributing to PostCompass

Thanks for your interest in PostCompass! Bug reports, ideas, docs fixes and pull requests are all welcome. This guide covers everything you need to build the app, find your way around the code and get a change merged.

PostCompass is maintained by one person ([@piyushg-07](https://github.com/piyushg-07)), so please be patient with reviews. By taking part you agree to follow the [Code of Conduct](CODE_OF_CONDUCT.md).

- **Found a bug?** [Open a bug report](https://github.com/piyushg-07/postcompass/issues/new?template=bug_report.yml).
- **Have an idea?** [Open a feature request](https://github.com/piyushg-07/postcompass/issues/new?template=feature_request.yml), or start a thread in [Discussions](https://github.com/piyushg-07/postcompass/discussions).
- **Found a security issue?** Please don't open a public issue. See [SECURITY.md](SECURITY.md).

## Prerequisites

| Tool | Version |
|---|---|
| [Node.js](https://nodejs.org) | 24 or newer |
| [pnpm](https://pnpm.io) | 12.15.0, pinned in `package.json`. Run `corepack enable` once and the right version is used automatically |
| [Rust](https://rustup.rs) | stable, pinned in `rust-toolchain.toml` (with `clippy` and `rustfmt`). The workspace uses edition 2024 and needs Rust 1.88 or newer |
| Platform tools | See [Tauri 2 prerequisites](https://tauri.app/start/prerequisites/) and below |

Platform-specific requirements for Tauri 2:

- **Windows:** [Microsoft C++ Build Tools](https://visualstudio.microsoft.com/visual-cpp-build-tools/) (the "Desktop development with C++" workload) and WebView2 (already installed on Windows 10 / 11).
- **macOS:** Xcode Command Line Tools (`xcode-select --install`).
- **Linux (Debian / Ubuntu):**

  ```bash
  sudo apt-get install -y libwebkit2gtk-4.1-dev libappindicator3-dev librsvg2-dev patchelf libdbus-1-dev pkg-config
  ```

  `libdbus-1-dev` is needed for the system keychain (Secret Service). These are the same packages CI installs.

## Getting started

```bash
git clone https://github.com/piyushg-07/postcompass.git
cd postcompass
corepack enable
pnpm install
pnpm dev            # starts the desktop app with hot reload
```

The first `pnpm dev` compiles the Rust backend and takes a few minutes; later runs are incremental.

> [!TIP]
> On Windows inside a synced folder (OneDrive, Dropbox), sync clients lock build files and break Cargo builds. Point Cargo's `target-dir` outside the synced folder in a local `.cargo/config.toml` (it's gitignored):
>
> ```toml
> [build]
> target-dir = "C:/Users/<you>/AppData/Local/postcompass/target"
> ```

## Commands

Run these from the repository root.

| Command | What it does |
|---|---|
| `pnpm dev` | Run the desktop app in development mode (Vite + `tauri dev`) |
| `pnpm build:app` | Build installers for your current OS (output in `target/release/bundle/`, or under your custom `target-dir`) |
| `pnpm check-types` | Type-check every TypeScript package |
| `pnpm lint` | Lint every package (zero warnings allowed) |
| `pnpm format` | Format TypeScript and Markdown with Prettier |
| `pnpm rust:check` | Clippy across the Rust workspace (all targets) |
| `pnpm rust:test` | Run the Rust tests |
| `pnpm rust:fmt` | Format the Rust code with `rustfmt` |

### Generated TypeScript bindings

The UI talks to Rust through typed commands generated by [tauri-specta](https://github.com/specta-rs/tauri-specta). **Debug builds** (`pnpm dev`) and `cargo test` regenerate [`apps/desktop/src/lib/bindings.ts`](apps/desktop/src/lib/bindings.ts) from the Rust command signatures.

Never edit `bindings.ts` by hand. If you add or change a Tauri command (or a type it uses), run the app or the tests once and **commit the updated `bindings.ts` together with the backend change**, otherwise `pnpm check-types` will fail for everyone else.

New commands must also be registered in `specta_builder()` in `apps/desktop/src-tauri/src/lib.rs`.

### End-to-end install test

`crates/runtime-postgres` has a slow end-to-end test that really downloads PostgreSQL, initializes, starts, queries, stops and uninstalls a server in a temp folder. It needs the network, so it's ignored by default:

```bash
cargo test -p runtime-postgres --test install_e2e -- --ignored --nocapture
```

Set `POSTCOMPASS_PG_ARCHIVE` to the path of an already-downloaded PostgreSQL archive to skip the download. Please run it if you touch install, start/stop or backup code.

## Checks before a pull request

Make sure these pass locally (they're what reviewers will run):

```bash
pnpm check-types && pnpm lint && pnpm rust:check && pnpm rust:test
```

And format your Rust code with `pnpm rust:fmt`.

## Architecture

```
┌──────────────────────────────┐        typed IPC          ┌─────────────────────────────────────┐
│  React 19 UI (apps/desktop)  │ ◄──── tauri-specta ────►  │  Rust core (apps/desktop/src-tauri) │
│  TanStack Query/Table/Form   │   generated bindings.ts   │  commands · state · keychain        │
│  Zustand · Radix · Tailwind  │                           └──────────────────┬──────────────────┘
└──────────────────────────────┘                                              │
                                     ┌────────────────────────────────────────┼─────────────────────────────┐
                                     ▼                                        ▼                             ▼
                             crates/pc-core                       crates/driver-postgres        crates/runtime-postgres
                             shared traits & types                connect · query · introspect  detect · install · start/stop
                             (DatabaseDriver, …)                  (tokio-postgres, TLS)          backup / restore
```

- **Modular by design.** Each database engine is a driver crate implementing the `DatabaseDriver` trait from `pc-core`; local server management implements the `LocalRuntime` trait. More engines can be added without touching the UI.
- **End-to-end types.** Rust commands export TypeScript types automatically, so the UI can't call the backend with the wrong shape.
- **Thin command layer.** `apps/desktop/src-tauri/src/commands/` maps UI calls onto the crates; the database logic lives in the crates so it can be tested without a window.
- **Secrets stay out of files.** Passwords go to Windows Credential Manager, macOS Keychain or Linux Secret Service (`secrets.rs`), never to `state.json`.
- **Locked-down webview.** A strict Content Security Policy and a minimal capability set (`apps/desktop/src-tauri/capabilities/default.json`): the UI can only use core APIs, the opener and file open/save dialogs.

## Project structure

```
postcompass/
├── apps/
│   ├── desktop/                # The PostCompass app (React + Tauri)
│   │   ├── src/
│   │   │   ├── app/            #   App shell, navigation, app state
│   │   │   ├── features/       #   backup, explorer, home, onboarding, palette, servers, settings
│   │   │   └── lib/            #   bindings.ts (generated), IPC and SQL helpers
│   │   └── src-tauri/          # Rust: commands/, state, keychain, window setup, tauri.conf.json
│   ├── server/                 # Small Hono API (experimental)
│   └── web/                    # Next.js website (placeholder)
├── crates/
│   ├── pc-core/                # Shared traits and types (DatabaseDriver, LocalRuntime, errors)
│   ├── driver-postgres/        # PostgreSQL driver: connect, query, introspect, DDL, row edits
│   └── runtime-postgres/       # Local PostgreSQL: detect, download, install, start/stop, backups
├── packages/
│   ├── ui/                     # Shared design system (tokens + components)
│   ├── eslint-config/
│   └── typescript-config/
├── docs/                       # PLAN.md, POSTGRES_GUIDE.md, assets/ (screenshots, banner)
└── .github/                    # Release workflow, issue and PR templates
```

The monorepo is managed with pnpm workspaces and [Turborepo](https://turborepo.dev) (JavaScript) plus a Cargo workspace (Rust) defined in the root `Cargo.toml`.

## Pull request workflow

1. **Discuss bigger changes first.** For anything beyond a small fix, open an issue or discussion so we can agree on the approach before you spend time on it.
2. **Fork and branch** from `main`. Use a short descriptive branch name, e.g. `fix/grid-null-paste` or `feat/roles-ui`.
3. **Keep it focused.** One logical change per pull request is much easier to review.
4. **Run the checks** above and commit `bindings.ts` if you changed backend commands.
5. **Open a pull request against `main`** and fill in the template. Include screenshots or a short clip for UI changes.
6. The maintainer reviews, may ask for changes, and merges.

UI changes should match the existing look: dense, Supabase-inspired layout, the shared components from `packages/ui` and the app's styled selects and menus (no native `<select>`).

## Commit messages

We use [Conventional Commits](https://www.conventionalcommits.org/):

```
<type>: <short summary in the imperative mood>
```

Common types, as seen in the history:

| Type | Use for |
|---|---|
| `feat` | A new feature or user-visible improvement |
| `fix` | A bug fix |
| `chore` | Maintenance, dependencies, lockfile, cleanup |
| `ci` | GitHub Actions and release automation |
| `docs` | Documentation only |
| `refactor` | Code changes that don't change behavior |
| `test` | Adding or fixing tests |

Examples from the log:

```
feat: brand Windows installers with the PostCompass logo
ci: polished release notes with download table and auto changelog
chore: remove unused apps/docs starter
```

An optional scope is fine (`fix(grid): ...`). Keep the summary under ~72 characters and explain the "why" in the body when it isn't obvious.

## Releasing

Releases are automated with GitHub Actions ([`.github/workflows/release.yml`](.github/workflows/release.yml)) and done by the maintainer:

1. Bump `"version"` in `apps/desktop/src-tauri/tauri.conf.json` (e.g. `0.2.0`), update [CHANGELOG.md](CHANGELOG.md), and commit.
2. Push that commit to the `release` branch:

   ```bash
   git push origin HEAD:release
   ```

3. CI builds installers for Windows (`.exe`, `.msi`), macOS Apple Silicon and Intel (`.dmg`) and Linux (`.AppImage`, `.deb`, `.rpm`), creates the tag `vX.Y.Z` and a **draft release** "PostCompass vX.Y.Z" with every file attached and GitHub's auto-generated "What's Changed" notes.
4. Open the draft on the [Releases page](https://github.com/piyushg-07/postcompass/releases), replace the **Highlights** bullets with what's new in this version, and click **Publish**.

Each release needs a new version number: pushing again with the same version updates the existing draft instead of creating a new one.
